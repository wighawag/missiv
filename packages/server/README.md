# @missiv/server

The platform-agnostic core of missiv: `createServer(options)` returns a Hono app serving missiv's HTTP API and room upgrades; a platform (`missiv`, `@missiv/bun`, `@missiv/cf-worker`) supplies the database, the rooms and the rate limiters.

- `migrate(db)` applies the numbered migrations (`src/schema/migrations/*.sql`) a database has not had; every platform calls it at start, except cf-worker, whose D1 database gets the same files through `wrangler d1 migrations apply`. 0.6's first migration (`0001_v0_6`) starts from an empty database: a database of 0.5 or earlier is not migrated, and fails to migrate rather than run on the wrong schema. `0002_v0_6_conversations` replaces its per-recipient copies with one row per message and an inbox row per member.
- The store ports (ADR-0005): `KeyDirectory`, `ConversationStore`, `Inbox` (`Stores`), by default `createSQLStores(getDB(env))` over `remote-sql` (a send is one transaction of six statements); a platform with its own stores passes `services.getStores`. Their contract suite is `test/store-contract.ts`, run here on libSQL and by `@missiv/bun` on bun:sqlite.
- `createInProcessRooms({getDB})` holds rooms and rate limiters in the process, for a long-lived server (nodejs, bun, a test).
- The live inbox channel (ADR-0006 "Live channel"): with `ServerOptions.liveInbox` (`createInProcessLiveInbox()` on nodejs and bun) the server serves `GET /api/inbox/ws`, the session token offered at the upgrade as `Sec-WebSocket-Protocol: missiv-inbox, <token>` (refused 401 before any socket otherwise), and pushes each new message and inbox row (`message`, `conversation` frames) to both members' open sockets, the sender's other devices included; a `sync` frame is answered with what the client missed, then `ready`; at the token's expiry the socket is closed with 4001 `session-expired`. The `LiveInbox` port is the seam a bus between several instances would implement (none is built).
- The polling transport: `POST /api/inbox/changes {domain, since}` answers `{version, unchanged: true}` when none of the account's inbox rows changed after the inbox version `since`, otherwise the rows that did (`Inbox.changes`, every row carrying its `version`). On Node.js and Bun an unchanged poll is answered from the process's memory while the socket is offered; with `INBOX_TRANSPORTS=poll` (several instances behind one load balancer) every poll reads its version from SQL.
- The push on a new direct message: `PUSH_SERVER_URL` and `PUSH_TOKENS`, or `ServerOptions.getPushNotifier` (a recording notifier in tests); it runs after the response (`ServerOptions.waitUntil`).
- Configuration: `SESSION_SECRET` (required), `SESSION_SECRET_PREVIOUS`, `ADMIN_TOKEN`, `SERVER_ORIGIN`, `PUSH_SERVER_URL`, `PUSH_TOKENS`, `PUSH_SKIP_WHEN_ONLINE` (`true`: no push to a recipient with the live channel's socket open), `INBOX_TRANSPORTS` (`socket,poll` by default; a transport left out answers 404), `EXPOSE_ERRORS`, `CHAIN_<chainId>`; see `docs/architecture.md`.

The server verifies the Ed25519 signature (delegated-identity's envelope) of each session opening and registration, and derives the caller from the account whose current key set signed it; every other request presents the session token it was given (an HMAC with `SESSION_SECRET`, checked with no database read). A send is on the token and authorized by the message's own Ed25519 signature, which the server verifies against the sender's current key set before storing it. It checks each registration's ownership proof (`recoverAccount`); the reading client checks everything again itself (`docs/adr/0003-the-client-verifies-the-server-relays.md`).
