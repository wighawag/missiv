# CONTEXT — missiv domain language

The domain glossary for `missiv`. Agents and skills use THIS vocabulary when naming modules, tests, and discussing the system. Architectural rationale lives in `docs/adr/` (decisions); the code-shape overview lives in `docs/architecture.md`; product framing lives in `work/specs/`.

## What missiv is

Missiv is a messaging system for Ethereum accounts. A backend stores messages that clients retrieve; messages are encrypted, but a sender can choose to send a clear-text introductory message to a recipient who has not yet published their public key, so first contact is possible before the recipient is registered. It ships as a pnpm/TypeScript monorepo: shared logic in `@missiv/common`, a `@missiv/server` and `@missiv/client`, and platform adapters for Bun, Cloudflare Workers, and Node.js.

## Core domain terms

- **account**: an Ethereum address (`0x…`, lowercase in missiv); the identity a user messages from and to.
- **key set**: an account's keys in one app (delegated-identity's `KeySet`): an Ed25519 **signing key**, which signs every request and message so the wallet is asked only once, and an X25519 **encryption key** others encrypt to. delegated-identity derives both from the account's **origin key** (`@etherplay/connect`'s per-origin secp256k1 key, which stays an on-chain signer and signs nothing in missiv), so every device of the account derives the same set. Named by its **keyRef** (`keySetRef`: SHA-256 of its two tagged keys). Replaces 0.5's secp256k1 **delegate key** (ADR-0004).
- **ownership proof**: the wallet's EIP-191 signature over the publication message of a key set for an **app origin** (the app's scheme, host and port, whose host is the domain). Its text is delegated-identity's `originPublicKeyPublicationMessage`, which `@etherplay/connect-core` imports (see `work/notes/findings/publication-message-shared-with-etherplay-connect.md`); connect saves it on the account as `savedPublicKeyPublicationSignature`.
- **registration**: a signed action (`ActionRegisterDomainUser`: account, domain, app origin, the key set, its ownership proof, a profile), signed by the key set's own signing key, making the account reachable with encrypted messages in one domain. One current key set per account and domain: registering it again (another device) keeps it, another key set replaces it (**key replacement**), and messages encrypted to the replaced one stay readable only with its keys. A key set, or a key of it, belongs to one (account, domain).
- **key directory**: the server's registered key sets: `getDomainUser` answers an account's current one, `getKeySet {domain, keyRef}` any one, current or replaced, so a reader still checks a message whose sender has since replaced their keys.
- **domain user**: an account's registration in one domain (`DomainUser`: its current key set and keyRef, its ownership proof and app origin, its profile there). There is no global profile.
- **request signature**: the signing key's Ed25519 signature over delegated-identity's request envelope (`delegated-identity ed25519 request v1`: server origin, route, timestamp, body's SHA-256), in the `SIGNATURE` header as `<timestamp>:<key>:<signature>`; the server verifies it against the key it names, derives the caller from the account whose current key set that is, and refuses it 60 s off or replayed. It authenticates only `register` and the opening of a **session (API)**, whose token authenticates everything else (a send also carries the message's own signature).
- **session (API)**: what one signed `POST /api/session` opens in a domain: a **session token** (`{account, domain, keyRef, exp}` HMAC'd with the server's `SESSION_SECRET`, about an hour) that authenticates every later request in that domain but `register`, with no signature check and no database read (ADR-0004, ADR-0006). `@missiv/client`'s `API` opens, renews and reopens it on its own. Not a room's session, which is one WebSocket connection to a room.
- **message (missiv message)**: the 0.6 format (`@missiv/common`'s `Message`, ADR-0004, ADR-0006 "The message"): one row and one `content` per message, read by every member, signed once by the sender's signing key over `missiv message` (domain, namespace, conversation, messageID, sender, `senderKeyRef`, scheme, keyID, the content's SHA-256). Its **messageID** is the client's ULID. Its **scheme** says how `content` is read: `clear` (the text) or `pairwise-v1` (1:1: AES-256-GCM under HKDF-SHA256 of the two members' X25519 shared secret, the **header** (the payload lines `domain` through `keyID`) as info and associated data); reserved `sender-key-v1`, `mls-v1`. Its **keyID** names the keys it is under: for `pairwise-v1` the two members' keyRefs, sorted, joined by `:`; null for `clear`; a later scheme's sender-key chain or MLS epoch. `@missiv/client`'s `composeMessage` / `composeIntroduction` build one, `openMessage` reads one. Stored once, under its **seq**: its place in the conversation, assigned by the ConversationStore from 1 (replaces 0.5's per-recipient **copy**). A send outside the messageID's 10-minute window is refused **stale** (with the server's time); a retry with the same messageID and signature answers the stored seq.
- **introductory message**: a `clear` (unencrypted) message, sent only when the user asks (`sendIntroduction`), to reach a recipient with no verified key; contrasts with an `encrypted` message. Never a fallback.
- **conversation**: a message thread between two accounts in one domain and namespace, identified by `(domain, namespace, conversationID)` (never the ID alone: the same two accounts talk separately per domain and namespace), its `conversationID` derived from the members (`conversationIDOf`: `getConversationID` of the two; a hash of the sorted addresses for more, refused while groups are); carries a **status** per member (`unaccepted`, `accepted`, `rejected`).
- **block**: rejecting a conversation blocks its other member in the whole domain: what they send is acknowledged to them and stored hidden from you (you never list it, are never pushed it) until `unblock`, or until you send them a message in the domain, which unblocks them as `unblock` does. The sender is not told.
- **inbox**: an account's conversation list, one row per conversation it is in (`Conversation`: status, `lastSeq` of the newest message it can see, `lastReadSeq`, `lastMessageAt`), ordered by last message, filtered by status; unread while `lastReadSeq < lastSeq`. Updated monotonically: an update applies only above the row's `lastSeq`. Its live side is the **live inbox channel**.
- **inbox version**: a counter per (domain, user) that every change of one of the user's inbox rows moves (each row records the version of its last change, `Conversation.version`); a write that changes no row (a repeated update, `unblock`) does not. What a poll asks about: "changed since version N?". Not a block's version (the Inbox object's per-block counter on Cloudflare, which orders a block's propagations).
- **live inbox channel**: one WebSocket per signed-in client (`GET /api/inbox/ws`, ADR-0006 "Live channel"), for one account in one domain (every namespace), its session token offered at the upgrade: the server pushes each new message the account can see (its own included, to its other devices) and each changed inbox row (`message`, `conversation` frames); after a (re)connection the client sends a **sync** (the last seq it holds per conversation) and gets what it missed, then `ready`; at the token's expiry the socket is closed `session-expired` and the client reconnects on a renewed token. A **heartbeat** keeps it (and every room socket) alive: the client sends the text frame `ping` every 30 s and the server answers `pong`; a socket with no answer within 10 s is given up and reconnected, and Node.js and Bun close one that sent nothing for 90 s (`heartbeat-timeout`, 4002). `@missiv/client`'s stores share it and do not poll themselves. Its **transport** is the socket or **polling** (`POST /api/inbox/changes`: the rows changed after the client's **inbox version**, or `unchanged`, then `listMessages {after}` for the messages it lacks), chosen by the client (`transport: 'socket' | 'poll' | 'auto'`, `auto` falling back to polling when the socket keeps failing) among those the deployment offers (`INBOX_TRANSPORTS`). Its server side is the Inbox's live side: the `LiveInbox` port in process on Node.js and Bun, and on Cloudflare the user's **Inbox object**, which holds the sockets and pushes its own frames (the server only routes the upgrade to it, `LiveInboxRouter`). Not a room's socket.
- **store ports**: `@missiv/server`'s `KeyDirectory` (the key directory and the replay set), `ConversationStore` (messages by seq, the one serialization point of a conversation) and `Inbox` (ADR-0005); one SQL implementation serves Node.js and Bun; Cloudflare has D1 for the KeyDirectory, a **Conversation object** (a Durable Object per conversation: its messages, and the inbox updates it retries by alarm until each member's Inbox object acknowledges) and an **Inbox object** (a Durable Object per (domain, user): its rows, its block list, which it propagates to the Conversation objects it shares with the blocked member, and its live sockets); all held to one contract suite.
- **domain**: the site/context a user is registered under; scopes users, conversations, and rooms.
- **room**: a public-chat channel (WebSocket-based). A room name is `@<domain>` for a public room, or `@<domain>!<authorization>` for a **semi-private room** whose read/write access is gated by an on-chain contract call encoded in the name (contract-gated, NOT encrypted). A room message carries no signature: the server attributes it to the session that sent it. See `docs/architecture.md`.
- **authorization (room)**: the `chainId:contractAddress:callData:expectedResult` string embedded after `!` in a room name; the server runs an `eth_call` (substituting the connecting account) and admits the session only if the result matches (rationale in `docs/adr/0001-contract-gated-room-authorization.md`). A session's identity and authorization are committed together, and every send checks them.
- **untrusted relay**: the core design principle: the missiv server stores and forwards; clients need NOT trust it for keys, authorship or content (only, best-effort, for delivery). The server verifies the **request signature** and the **session token** (who may write, as which account) and each registration's ownership proof; the client verifies every **ownership proof** before using a key set and every message's signature before showing it, and decrypts each message on its own into its text or an `unverified` / `undecryptable` error. Rationale and known limits (non-deterministic wallets, no forward secrecy, metadata, rooms): `docs/adr/0003-the-client-verifies-the-server-relays.md`.
- **push**: a new direct message is pushed to its recipient (not the sender, not one who blocked them, not a retry, and with `PUSH_SKIP_WHEN_ONLINE` not one who has the live inbox channel open) through push-notification-server, with the domain's token, naming the sender and the conversation and never the content. Not the live channel's frames, which are pushed on a socket.
- **load harness**: `test/load` (`pnpm load <send|read|list|live|room|all>`), many simulated clients with real key sets driving a server over HTTP and WebSockets; reports throughput and p50/p95/p99 latency per scenario. Its **API adapter** (`--api`, `src/adapters/`) is one API version's client side (0.6 today): not to be confused with a **platform adapter**, which is a server runtime.
- **token bucket (rate limit)**: `@missiv/server`'s budget of requests per key (`TokenBuckets`, `src/rate-limit.ts`): `burst` tokens refilled at a rate, one per request; beyond it a request is refused `rate_limited` with `retryAfterMs`. The `send` bucket is per account and domain (never per IP), the `ip` bucket per client IP on `/api/session` and `register`. Not a room's **rate limiter** (`RateLimiter`), a server object per IP that a room consults over fetch.
- **platform adapter** — a per-runtime host (`platforms/bun`, `platforms/cf-worker`, `platforms/nodejs`) that wires `@missiv/server` to a concrete storage / server-object / rate-limiter implementation.
- **promptGuidance** — the per-repo NUDGE namespace in `dorfl.json` whose members (currently just `testFirst`) strengthen the wording in the worker's in-band prompt. NOT a gate: the `verify` step is still the only acceptance bar. Omitted ⇒ off; absence is the default.
- **work/ contract** — the on-disk system this repo uses, defined by the reference docs in **`work/protocol/`** (copied here by `setup`): `WORK-CONTRACT.md` (the contract), `CLAIM-PROTOCOL.md`, `REVIEW-PROTOCOL.md`, `task-template.md`, `spec-template.md`, `ADR-FORMAT.md`. Three REGIME umbrellas — `notes/` (capture buckets), `tasks/` (the build board), `specs/` (the spec lifecycle) — plus top-level `questions/` and `protocol/`. One markdown file per item, status = the folder it lives in (never a field). Capture buckets: `notes/ideas/` (proposed), `notes/observations/` (spotted, unverified, append-only), `notes/findings/` (verified external/domain ground truth, each with a `source:`). ADRs (`docs/adr/`, format in `work/protocol/ADR-FORMAT.md`) record what WE decided and why.

## Conventions

Standing per-change rules agents must follow in this repo.

- **Every change requires a changeset.** Run `pnpm changeset` and commit the generated file with your change (this repo uses `@changesets/cli`). For enforcement, wire `changeset status --since=main` into the `dorfl.json` `verify` gate yourself.
