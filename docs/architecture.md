# missiv architecture (code-shape overview)

A description of how missiv's own code is laid out. This is current-truth about OUR code (it changes as the code changes); external ground-truth we integrate with lives in `work/notes/findings/`, and decisions-with-rationale live in `docs/adr/`.

## Monorepo layout

A pnpm workspace (`pnpm-workspace.yaml`) with three groups:

- `packages/*`
  - **`@missiv/common`**: the protocol. Every request and response of the HTTP API as a zod schema with its type inferred from it (the server validates exactly what the client is typed against), the error codes and their statuses, the room messages, `conversationIDOf`, the key set as registered (`PublicKeySetSchema`, the `KeySet`/`PublicKeySet` types of delegated-identity), and the copy signature (`messageCopyMessage`, `signMessageCopy`, `verifyMessageCopy`: Ed25519 through `delegated-identity/ed25519`). The key set's derivation, the publication message, the request envelope and their verifiers are delegated-identity's, imported directly by the server and the client (nothing of them is copied or re-exported here). No runtime host.
  - **`@missiv/server`**: the server core, platform-agnostic: `createServer(options)` (a Hono app: `/api/session`, `/api/user`, `/api/private`, `/api/public` with the room upgrade, `/api/admin`), the `setup` middleware, which checks a request's session token (`session.ts`: an HMAC with `SESSION_SECRET`, no database read) and, when the request is signed, verifies its Ed25519 signature against the key it names and finds the domain user whose current key set that key signs for (the routes then require one or the other: `requireAccount` the token, `requireSignedAccount` and `requireSigner` the signature), the key directory (`KeySets`, every key set registered in a domain by keyRef, current or replaced; `DomainUsers`, each account's current one), `RemoteSQLStorage` over `remote-sql`, the numbered migrations (`src/schema/migrations/*.sql`, applied by `migrate(db)`), the `Room` base class and its in-process implementation (`createInProcessRooms`: rooms and rate limiters held in a Map, for one long-lived process), and the push notifier (`createHTTPPushNotifier`, `pushNotifierFromEnv`).
  - **`@missiv/client`**: a Svelte library (`src/lib`, published) plus a demo app (`src/routes`, `src/app`). The library: `API` (typed calls taking the account's signing key: `register` and `sendMessage` signed with delegated-identity's Ed25519 envelope, every other call on a session token the `API` opens per domain and key with one signed `POST /api/session`, renews five minutes before it expires and opens again once when it is refused; a refusal thrown as `MissivAPIError` with its status and code), `messages.ts` (what the client trusts: `verifyDomainUser` and `verifyKeySet` check a key set against its wallet with delegated-identity, `encryptedCopies`, `clearCopies`, `openMessage`), and four stores on one lifecycle (`utils/lifecycle.ts`'s `activeStore`: work only while subscribed, for the registration's current account): `createMissivRegistration` (its account is `@etherplay/connect`'s signed-in account: the address, the key set with its private keys, the saved ownership signature), `openConversationList`, `openOneConversation`, `openRoom`. The demo app signs in with `@etherplay/connect` and registers the account's key set with its saved ownership signature.
- `platforms/*`: per-runtime hosts: **`nodejs`** (`createNodeServer({db, env})`: libSQL, migrated at start, rooms in process on `@hono/node-ws`; the CLI `missiv`), **`bun`** (bun:sqlite with real transactions, rooms in process), **`cf-worker`** (D1, migrated by `wrangler d1 migrations apply` from the same files, rooms and rate limiters as Durable Objects with hibernation).
- `test/*`: cross-cutting tests, `client-server`: the server in process (`app.request` on in-memory libSQL, no port), driven through @missiv/client with real wallets and origin keys, each user's key set derived by delegated-identity; the client's stores driven the same way, the room through fake sockets wired to an in-process room. Its users and their signed actions (`createUser`, `createActions(api)` in `test/setup.ts`) serve any `API`, in process or over HTTP. `load`: the load harness (`pnpm load <scenario>`, not part of `pnpm test`), which drives a server over real HTTP and WebSockets (the Node.js platform in a worker thread, the Bun platform as a child process, or any URL) through one adapter per API version (`src/adapters/`), and prints throughput and p50/p95/p99 latencies; its numbers go to `work/notes/findings/` (the 0.5 baseline: `load-baseline-0-5.md`).

## Configuration (every platform's env)

- `SESSION_SECRET` (required, a long random secret): the HMAC-SHA256 key of session tokens. Every route that authenticates its caller (`/api/session`, `register`, `sendMessage` and every route taking a token) is refused `forbidden` while it is unset, as the admin API is without `ADMIN_TOKEN`; the public reads (`getDomainUser`, `getKeySet`, rooms) still answer. The `dev` scripts of the three platforms set a dev-only one when none is given.
- `SESSION_SECRET_PREVIOUS` (optional): the secret being rotated out. Tokens signed with it are accepted until they expire (an hour); new ones are signed with `SESSION_SECRET`. To rotate: move the current secret here, set a new `SESSION_SECRET`, and drop this one after an hour.
- `ADMIN_TOKEN`: the bearer token of `/api/admin` (`db-reset`); every admin request is refused when it is unset.
- `SERVER_ORIGIN`: the server's origin as clients address it, which every request signature names; defaults to the request URL's origin (set it behind a proxy that rewrites the host or the scheme).
- `PUSH_SERVER_URL` and `PUSH_TOKENS` (`<domain>=<token>,...`, the tokens push-notification-server issued, held as secrets): a new direct message is pushed to its recipients; a domain without a token sends none.
- `EXPOSE_ERRORS=true`: an internal error's cause and stack go to the caller (never in production).
- `CHAIN_<chainId>`: a chain's JSON-RPC endpoint, for contract-gated rooms.
- nodejs: `DB`, a libSQL URL (`:memory:` by default).

## Sessions

ADR-0004 decision 5 and ADR-0006 "Sessions and replay". A client opens a session in a domain with `POST /api/session {domain}`, a request signed by the signing key of its current key set there; the server answers `{token, expiresAt, keyRef}`. The token is `<payload>.<mac>`: the base64url JSON of `{account, domain, keyRef, exp}` (`exp` in ms) and the base64url HMAC-SHA256 of that payload under `SESSION_SECRET`, an hour long (`packages/server/src/session.ts`, which also records the choices the ADR left open). Every later request in the domain presents it as `Authorization: Bearer <token>`; the `setup` middleware checks it with an HMAC and a constant-time comparison and reads nothing, and a route refuses `unauthenticated` a missing, invalid, expired or other-domain token. Two routes keep the request signature: `register` (it proves its key set itself) and `sendMessage` (with `refuseReplay`, until the message signature authorizes a send, task `sqlite-conversation-store-and-api`). The replay set (`RequestSignatures`, `refuseReplay`) remembers each accepted session request, registration and send for its 60 s window. A token issued before its key set was replaced stays valid until it expires: no request reads the directory to find out. Room logins are unchanged (spec `scalable-rooms`).

## Trust

The server verifies requests (who may write, as which account, in which domain); the client verifies keys and messages (whose key, whose message). See CONTEXT.md's "untrusted relay" and `docs/adr/0003-the-client-verifies-the-server-relays.md`.

## Two messaging surfaces

missiv has two distinct message paths:

1. **Stored async messaging** (inbox / conversations): the action/response protocol in `@missiv/common` (`ActionSendMessage`, `getConversations`, `acceptConversation`, `rejectConversation`, `unblock`, `markAsRead`, `getMessages`, …), lists and messages by cursor page. A message is one signed copy per member, `encrypted` or `clear` (0.5's format on 0.6's key sets until the one-ciphertext format); a `clear` message is the introduction a user asks for, to a recipient with no verified key.
2. **Real-time rooms** (public chat) — the WebSocket `Room` class in `packages/server/src/Room.ts`. Clients connect to `@<domain>` (public) or `@<domain>!<authorization>` (semi-private). The server keeps in-memory `Session`s, buffers a message backlog (last 100) from storage, broadcasts to connected sessions, and enforces a per-IP rate limit.

## Semi-private (contract-gated) rooms

A room name of the form `@<domain>!<authorization>` carries an `authorization` string `chainId:contractAddress:callData:expectedResult`. On a session's login (an `address` message with the Ed25519 request signature of the account's current signing key over the socket's challenge, method `GET` and the room's path), if the room has an authorization the server substitutes the connecting account into `callData` (the `(address)` placeholder), performs an `eth_call` against the chain RPC configured as `CHAIN_<chainId>`, and only marks the session `authorized` (releasing its buffered messages and allowing sends) if the returned value equals `expectedResult`. Access control is therefore contract-defined and public/unencrypted: anyone the contract admits can read and write. (See the room-authorization finding in `work/notes/findings/`.)

## Storage & platform seams

`@missiv/server` talks to storage through the `remote-sql` abstraction (`RemoteSQLStorage`), so each platform supplies its own SQL backend (e.g. libsql for the local/dev and Node paths, Cloudflare's binding on the worker). The `Room` base class defers `getDB` and `getRateLimiter` to the subclass, which the platform adapter provides. Cloudflare's hibernation is handled by serialising socket metadata (`saveSocketData` / `retrieveSocketData`); non-hibernating platforms (Bun) treat those as no-ops.
