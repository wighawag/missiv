# missiv architecture (code-shape overview)

A description of how missiv's own code is laid out. This is current-truth about OUR code (it changes as the code changes); external ground-truth we integrate with lives in `work/notes/findings/`, and decisions-with-rationale live in `docs/adr/`.

## Monorepo layout

A pnpm workspace (`pnpm-workspace.yaml`) with three groups:

- `packages/*`
  - **`@missiv/common`**: the protocol. Every request and response of the HTTP API as a zod schema with its type inferred from it (the server validates exactly what the client is typed against), the error codes and their statuses, the room messages, `conversationIDOf`, the key set as registered (`PublicKeySetSchema`, the `KeySet`/`PublicKeySet` types of delegated-identity), the missiv message (`message.ts`, ADR-0006 "The message": the `Message` type and its zod schemas, the signing payload, `signMessage` / `verifyMessage` with Ed25519 through `delegated-identity/ed25519`, and `pairwise-v1`'s `encryptPairwise` / `decryptPairwise`; pinned by test vectors in `message.test.ts`), its one cipher module (`cipher.ts`: X25519, HKDF-SHA256, AES-256-GCM through WebCrypto when `crypto.subtle` exists, `@noble` otherwise, as on a plain-http origin), `newULID` / `ulidTime` / `ulidAt` (the client's messageIDs and the server's window check), `membersOfConversationID` (the two members a 1:1 conversationID names), the live inbox channel's wire (`inbox.ts`: `INBOX_WS_PATH`, `INBOX_WS_PROTOCOL`, the `session-expired` close code, `InboxSyncSchema`, `InboxServerFrame`, `inboxConversationKey`), and the 0.6 messaging actions (`ActionSendMessage` carrying one `MessageToSend`, `listMessages` by seq, `listConversations`, `accept`, `reject`, `unblock`, `markRead`, the `Conversation` of one member's inbox with `lastSeq` / `lastReadSeq`, `MESSAGE_ID_WINDOW_MS` and the `stale` error code). The key set's derivation, the publication message, the request envelope and their verifiers are delegated-identity's, imported directly by the server and the client (nothing of them is copied or re-exported here). No runtime host.
  - **`@missiv/server`**: the server core, platform-agnostic: `createServer(options)` (a Hono app: `/api/session`, `/api/user`, `/api/messages` (the send), `/api/private` (the messaging reads and status changes), `/api/public` with the room upgrade, `/api/inbox/ws` (the live inbox channel, where the platform holds its sockets), `/api/admin`), the `setup` middleware, which checks a request's session token (`session.ts`: an HMAC with `SESSION_SECRET`, no database read) and, when the request is signed, verifies its Ed25519 signature against the key it names and finds the domain user whose current key set that key signs for (the routes then require one or the other: `requireAccount` the token, `requireSignedAccount` and `requireSigner` the signature), the store ports of ADR-0005 (`src/stores/ports.ts`: `KeyDirectory`, `ConversationStore`, `Inbox`, together `Stores`, and the Inbox's live side `LiveInbox` (`publish` frames to a user's sockets, `isOnline`), held in process by `createInProcessLiveInbox` (`src/live.ts`) and passed as `ServerOptions.liveInbox`; a platform may supply its own through `services.getStores`) and their one SQL implementation over `remote-sql` (`src/stores/sql/`, `createSQLStores(db)`: the key directory's `KeySets`, every key set registered in a domain by keyRef, current or replaced, and `DomainUsers`, each account's current one; `Messages`, one row per message keyed by `(domain, namespace, conversationID, seq)` with a unique messageID; `Inbox`, one row per member with `lastSeq`, `lastReadSeq` and the list indexes; `Blocks`), whose contract suite (`packages/server/test/store-contract.ts`) runs on libSQL under vitest and on bun:sqlite under `bun test`, the numbered migrations (`src/schema/migrations/*.sql`, applied by `migrate(db)`), the `Room` base class and its in-process implementation (`createInProcessRooms`: rooms and rate limiters held in a Map, for one long-lived process; an idle rate limiter is evicted), the token buckets (`src/rate-limit.ts`, see "Rate limits"), what follows a stored message or a changed inbox row (`src/delivery.ts`: the live frames, then the push), and the push notifier (`createHTTPPushNotifier`, `pushNotifierFromEnv`).
  - **`@missiv/client`**: a Svelte library (`src/lib`, published) plus a demo app (`src/routes`, `src/app`). The library: `API` (typed calls taking the account's signing key: `register` signed with delegated-identity's Ed25519 envelope, every other call (`sendMessage`, whose message carries its own signature, included) on a session token the `API` opens per domain and key with one signed `POST /api/session`, renews five minutes before it expires and opens again once when it is refused; a refusal thrown as `MissivAPIError` with its status and code), `messages.ts` (what the client trusts: `verifyDomainUser` and `verifyKeySet` check a key set against its wallet with delegated-identity, `composeMessage` and `composeIntroduction` build a missiv message, `openMessage` checks and reads one, fetching the sender's key set by `senderKeyRef` through `getKeySet`), the live inbox channel (`inbox/`: `openInboxChannel`, ONE WebSocket per endpoint, domain and signing key, shared by the stores of that account, open while one listens, its token from `API.getSession`, reconnected with backoff and at once on `session-expired` with a renewed token), and four stores on one lifecycle (`utils/lifecycle.ts`'s `activeStore`: work only while subscribed, for the registration's current account; none polls): `createMissivRegistration` (its account is `@etherplay/connect`'s signed-in account: the address, the key set with its private keys, the saved ownership signature), `openConversationList` (`listConversations` each time the channel opens, then the pushed inbox rows, by `lastSeq`; unread from `lastReadSeq`), `openOneConversation` (the newest page once, then the pushed messages, each seq opened once, and a `sync` after the last seq it has on every (re)connection; a sent message shown from the send's answer; a `stale` send composed again under the server's time), `openRoom`. The demo app signs in with `@etherplay/connect` and registers the account's key set with its saved ownership signature.
- `platforms/*`: per-runtime hosts: **`nodejs`** (`createNodeServer({db, env})`: libSQL, migrated at start, rooms in process on `@hono/node-ws`; the CLI `missiv`), **`bun`** (`createBunServer({db, env})`: bun:sqlite with real transactions, rooms in process; Bun 1.3.13 or later; its tests, the store contract and the platform's boot, run under `bun test` and are skipped with a warning where bun is absent, or fail with `REQUIRE_BUN=1`), **`cf-worker`** (D1 for the same SQL stores as an interim until its Durable Object stores, migrated by `wrangler d1 migrations apply` from the same files, rooms and rate limiters as Durable Objects with hibernation).
- `test/*`: cross-cutting tests, `client-server`: the server in process (`app.request` on in-memory libSQL, no port), driven through @missiv/client with real wallets and origin keys, each user's key set derived by delegated-identity; the client's stores driven against the same app served on a loopback port (`listen()`, with `@hono/node-ws` as the Node.js platform), their live inbox channel a real WebSocket, the room through fake sockets wired to an in-process room. Its users and their signed actions (`createUser`, `createActions(api)` in `test/setup.ts`) serve any `API`, in process or over HTTP. `load`: the load harness (`pnpm load <scenario>`, not part of `pnpm test`), which drives a server over real HTTP and WebSockets (the Node.js platform in a worker thread, the Bun platform as a child process, or any URL) through one adapter per API version (`src/adapters/`: `0.6`, and `0.6-page` whose read is the newest page), and prints throughput and p50/p95/p99 latencies; its numbers go to `work/notes/findings/` (the 0.5 baseline: `load-baseline-0-5.md`; 0.6 on the SQL stores: `load-0-6-sql-stores.md`).

## Configuration (every platform's env)

- `SESSION_SECRET` (required, a long random secret): the HMAC-SHA256 key of session tokens. Every route that authenticates its caller (`/api/session`, `register` and every route taking a token, the send included) is refused `forbidden` while it is unset, as the admin API is without `ADMIN_TOKEN`; the public reads (`getDomainUser`, `getKeySet`, rooms) still answer. The `dev` scripts of the three platforms set a dev-only one when none is given.
- `SESSION_SECRET_PREVIOUS` (optional): the secret being rotated out. Tokens signed with it are accepted until they expire (an hour); new ones are signed with `SESSION_SECRET`. To rotate: move the current secret here, set a new `SESSION_SECRET`, and drop this one after an hour.
- `ADMIN_TOKEN`: the bearer token of `/api/admin` (`db-reset`); every admin request is refused when it is unset.
- `SERVER_ORIGIN`: the server's origin as clients address it, which every request signature names; defaults to the request URL's origin (set it behind a proxy that rewrites the host or the scheme).
- `PUSH_SERVER_URL` and `PUSH_TOKENS` (`<domain>=<token>,...`, the tokens push-notification-server issued, held as secrets): a new direct message is pushed to its recipients; a domain without a token sends none.
- `RATE_LIMIT_SEND_BURST` and `RATE_LIMIT_SEND_REFILL_PER_SECOND` (default 20 and 1): the token bucket of each account's sends; `RATE_LIMIT_IP_BURST` and `RATE_LIMIT_IP_REFILL_PER_SECOND` (default 30 and 0.5): the bucket of each client IP on `/api/session` and `register`. A value that is not a positive number fails the request that reads it. See "Rate limits".
- `PUSH_SKIP_WHEN_ONLINE=true` (optional, off by default): no push to a recipient who has the live inbox channel open in the message's domain (it got the message on the socket); one without a socket is pushed as before. Only where the platform holds the sockets (nodejs, bun).
- `EXPOSE_ERRORS=true`: an internal error's cause and stack go to the caller (never in production).
- `CHAIN_<chainId>`: a chain's JSON-RPC endpoint, for contract-gated rooms.
- nodejs: `DB`, a libSQL URL (`:memory:` by default).

## Sessions

ADR-0004 decision 5 and ADR-0006 "Sessions and replay". A client opens a session in a domain with `POST /api/session {domain}`, a request signed by the signing key of its current key set there; the server answers `{token, expiresAt, keyRef}`. The token is `<payload>.<mac>`: the base64url JSON of `{account, domain, keyRef, exp}` (`exp` in ms) and the base64url HMAC-SHA256 of that payload under `SESSION_SECRET`, an hour long (`packages/server/src/session.ts`, which also records the choices the ADR left open). Every later request in the domain presents it as `Authorization: Bearer <token>`; the `setup` middleware checks it with an HMAC and a constant-time comparison and reads nothing, and a route refuses `unauthenticated` a missing, invalid, expired or other-domain token. One route keeps the request signature: `register` (it proves its key set itself). A send (`/api/messages/send`) is on the token, and authorized by the message's own signature (see "Sending" below). The replay set (`RequestSignatures`, `refuseReplay`) remembers each accepted session request and registration for its 60 s window; a send needs none (its messageID is its replay guard). A token issued before its key set was replaced stays valid until it expires: no request reads the directory to find out. Room logins are unchanged (spec `scalable-rooms`).

## Sending (ADR-0006 "Sending")

`POST /api/messages/send {type: 'sendMessage', message}`: the token's account and key set must be the message's `sender` and `senderKeyRef`, the conversationID a 1:1 one (`otherMemberOf` in `src/api/conversation.ts`: the members are the ID, refused `invalid_request` for another form, `forbidden` for a non-member), a `pairwise-v1` keyID must name the sender's key set, the messageID's ULID time within 10 minutes of the server's clock (else `stale` with `details.serverTime`), the key set the sender's current one (one directory read) and the signature valid for it; then one `ConversationStore.append`. On SQL that is one transaction of five statements, each a key lookup, whatever the history (asserted by the contract suite, with the query plans): the read of a message already under the messageID, the insert under the next seq (the previous seq read backwards on the primary key) with `hiddenFrom` set when the recipient blocked the sender in the domain, the sender's and the recipient's inbox rows (the recipient's only when not hidden; both monotonic on `lastSeq`), and the stored row with the recipient's app origin, which the push uses. A retry (the same messageID and signature) answers the stored seq, another signature `conflict`. A message hidden from its recipient is acknowledged like any other; the recipient never lists it, is never pushed it, and its inbox row does not move.

After an append (not a retry), after the response (`src/delivery.ts`): the message and each member's inbox row to that member's open sockets (`message`, `conversation` frames; the sender's included, for its other devices; not the member it is hidden from), an inbox row read only for a member who is online; then the push. `accept`, `reject` and `markRead` push the changed row to the user's own sockets.

## Rate limits

Spec `scalable-direct-messaging` story 27 (`packages/server/src/rate-limit.ts`). Token buckets, each `burst` tokens refilled at a rate, one token per request, a refused request taking none: `send`, per account and domain, charged by `messages/send` right after the token's check (before the signature check and any read), never per IP, so accounts behind one IP keep their own budgets; `ip`, per client IP, charged by `/api/session` and `register` together before anything else of the route (`limitPerIP`). A refusal is `rate_limited` (429) with `details.retryAfterMs` (`RateLimitedDetails`) and `Retry-After` in seconds. The IP is `ServerOptions.getIP` (Node: the socket's address; Bun: `requestIP`; Cloudflare: `CF-Connecting-IP`); a request whose IP is unknown is not limited per IP. The buckets are `ServerOptions.getTokenBuckets`, by default held in process (`createInProcessTokenBuckets`): a bucket refilled to its burst is evicted by a sweep at most once per refill time, and at most 100 000 keys are held (least recently used dropped). On Cloudflare that is per isolate, an approximation until task `cloudflare-durable-object-stores` holds the send's bucket in the Inbox Durable Object. Rooms keep their own `RateLimiter` (one action per 5 s per IP past a 20 s grace, spec `scalable-rooms`); `createInProcessRooms` now evicts an idle one, and hands rooms a stub that looks its limiter up at each call, so an eviction never splits an IP's budget.

## Live inbox channel (ADR-0006 "Live channel")

`GET /api/inbox/ws` (`src/api/inbox/index.ts`), served where the platform holds the sockets (`ServerOptions.liveInbox`: nodejs and bun, `createInProcessLiveInbox`, a Map of each (domain, user)'s sockets; cf-worker has no route until its Inbox Durable Object). The session token is checked BEFORE the socket is accepted, offered as `Sec-WebSocket-Protocol: missiv-inbox, <token>` (the server selects `missiv-inbox`); a missing, forged or expired one is refused 401 `unauthenticated` and no socket opens. A socket covers the token's domain, every namespace. The client may send `{type: 'sync', since: {'<namespace>:<conversationID>': seq}}` (at most 1000 conversations); the server answers each conversation the account is a member of with every message after that seq it can see (paged, in seq order) and its inbox row, then `{type: 'ready'}`, syncs in the order sent; anything else closes the socket (1008). At the token's `exp` the server closes it with 4001 `session-expired`. Frames may repeat or arrive out of order: the client applies messages by seq and rows by `lastSeq`. The wire's choices are recorded in `packages/common/src/inbox.ts`. Several instances would put a bus behind the `LiveInbox` port; none is built.

## Trust

The server verifies requests (who may write, as which account, in which domain); the client verifies keys and messages (whose key, whose message). See CONTEXT.md's "untrusted relay" and `docs/adr/0003-the-client-verifies-the-server-relays.md`.

## Two messaging surfaces

missiv has two distinct message paths:

1. **Stored async messaging** (inbox / conversations): the action/response protocol in `@missiv/common` (`ActionSendMessage`, `listMessages`, `listConversations`, `accept`, `reject`, `unblock`, `markRead`), messages by seq (`after` what the client has, `before` to page back, always in seq order), conversation lists from each member's inbox index by a `lastMessageAt:conversationID` cursor. A message is one row, `pairwise-v1` or `clear`, read by both members; a `clear` message is the introduction a user asks for, to a recipient with no verified key.
2. **Real-time rooms** (public chat) — the WebSocket `Room` class in `packages/server/src/Room.ts`. Clients connect to `@<domain>` (public) or `@<domain>!<authorization>` (semi-private). The server keeps in-memory `Session`s, buffers a message backlog (last 100) from storage, broadcasts to connected sessions, and enforces a per-IP rate limit (its `RateLimiter`, not the token buckets of "Rate limits").

## Semi-private (contract-gated) rooms

A room name of the form `@<domain>!<authorization>` carries an `authorization` string `chainId:contractAddress:callData:expectedResult`. On a session's login (an `address` message with the Ed25519 request signature of the account's current signing key over the socket's challenge, method `GET` and the room's path), if the room has an authorization the server substitutes the connecting account into `callData` (the `(address)` placeholder), performs an `eth_call` against the chain RPC configured as `CHAIN_<chainId>`, and only marks the session `authorized` (releasing its buffered messages and allowing sends) if the returned value equals `expectedResult`. Access control is therefore contract-defined and public/unencrypted: anyone the contract admits can read and write. (See the room-authorization finding in `work/notes/findings/`.)

## Storage & platform seams

`@missiv/server`'s routes talk to the store ports and the live inbox (`ServerOptions.liveInbox`) (`Stores`: `KeyDirectory`, `ConversationStore`, `Inbox`, ADR-0005), by default the SQL ones over the `remote-sql` abstraction (`createSQLStores(getDB(env))`), so each platform supplies its own SQL backend (libsql on Node, bun:sqlite on Bun, D1 on the worker for now) or its own stores (`services.getStores`, for Cloudflare's Durable Objects). A store that keeps inboxes apart from conversations returns the inbox updates it did not apply (`pendingInboxUpdates`) and the send route applies them with `Inbox.update`; the SQL store applies them in the append's transaction and returns none. The `Room` base class defers `getDB` and `getRateLimiter` to the subclass, which the platform adapter provides. Cloudflare's hibernation is handled by serialising socket metadata (`saveSocketData` / `retrieveSocketData`); non-hibernating platforms (Bun) treat those as no-ops.
