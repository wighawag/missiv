# Decisions made while building one-ciphertext-message-format

In-scope choices ADR-0006 left open, one per entry, for the reviewer and the human to ratify or reverse. The wire-format ones (1 to 3) are pinned by the test vectors in `packages/common/src/message.test.ts`, so changing one means changing the vectors.

1. **`pairwise-v1`'s keyID is the two keyRefs, lowercase, sorted ascending, joined by `:`** (`0x…:0x…`). ADR-0006 says "sorted, joined" without a separator. Alternative: concatenation, as `getConversationID` does for its two addresses (in descending order); `:` reads better and parses without knowing the length. The schema refuses an unsorted keyID. Touches `sqlite-conversation-store-and-api` (it stores and may index keyID). Site: `packages/common/src/message.ts` header and `pairwiseKeyID`.
2. **`content` of `pairwise-v1` is unpadded base64url** (RFC 4648 section 5 without `=`, `@scure/base`'s `base64urlnopad`) of IV (12 bytes), ciphertext and 16-byte tag; the decoder refuses padding. Alternative: padded. Site: `message.ts` header.
3. **The header fields' formats**, so no value can hold a newline: domain 1 to 253 printable ASCII characters without space, namespace up to 64 characters without control characters, conversationID either `getConversationID`'s two addresses or a 32-byte hex hash (the group form, refused by the server while groups are), messageID an uppercase Crockford ULID, sender a lowercase address, senderKeyRef a lowercase 32-byte hex keyRef, signature 64 lowercase hex bytes, `content` at most 16384 characters (`MAX_MESSAGE_CONTENT_LENGTH`, as today's copies), `seq` and `serverTimestamp` non-negative integers. These are message-local schemas: the shared `DomainSchema` / `NamespaceSchema` of the other actions are unchanged (no new refusal elsewhere). `signMessage` and `messageSigningPayload` throw on an invalid message; `verifyMessage` answers false. Touches `sqlite-conversation-store-and-api` (its `messages/send` parses with `MessageToSendSchema`). Site: `message.ts`.
4. **The new format sits beside the interim per-copy one, which keeps working until `sqlite-conversation-store-and-api`**: the server still stores copies (and generates their ids), so the stores keep `encryptedCopies` / `clearCopies` and the per-copy reader, renamed `openMessageCopy` (and `OpenedMessageCopy`) so that `openMessage` / `OpenedMessage` are the new format's, as the task names them. A breaking rename in `@missiv/client`. The interim path keeps xchacha20poly1305 and keccak until that task removes it; the new format has neither. Alternative: name the new reader differently and rename later (two renames), or move the stores now (the next task's scope). Site: `packages/client/src/lib/messages.ts` header.
5. **The client composes with `composeMessage` (`pairwise-v1`) and `composeIntroduction` (`clear`)**, two functions rather than one with a `scheme` flag, so a clear message is never a fallback of an encrypted one (CONTEXT's "introductory message"). They take `destination: {domain, namespace}`, derive `conversationID` with `conversationIDOf`, compute both keyRefs with `keySetRef`, and draw a ULID messageID unless one is given (a retry reuses it). Composing to oneself throws. Site: their JSDoc.
6. **`openMessage` fetches key sets through a `KeySetSource`** (anything with `API`'s `getKeySet`), caching each answer per source and (domain, keyRef) since a key set never changes once registered, and checking it on every use. A `getKeySet` that throws (server unreachable) is thrown, not turned into `unverified`, and nothing is cached, so a retry can succeed; a missing key set is `unverified`. Alternative: report a fetch failure as `unverified` (wrong verdict, and cached). Touches the stores of `sqlite-conversation-store-and-api`, which must catch it per page. Site: `openMessage`'s JSDoc.
7. **The sender reading its own `pairwise-v1` message fetches the other key set by the other keyRef of `keyID` and checks only that `keySetRef` of it is that keyRef**, not its ownership proof: the keyID is covered by the sender's verified signature, and the key is used only to decrypt. The recipient checks the sender's key set fully (keyRef and ownership proof) before the signature. Site: `openMessage`'s JSDoc.
8. **Verdicts beyond the task's list**: a sender who is not one of the two members of a 1:1 conversationID is `unverified`; a reader whose keyRef is not in `keyID`, or a keyID not naming `senderKeyRef`, is `undecryptable`; a message of a scheme this client does not know (`sender-key-v1`, `mls-v1`) is `undecryptable` without being verified (the schema accepts only known schemes). Site: `openMessage`.
9. **The cipher module chooses per primitive**: HKDF and AES-GCM through WebCrypto whenever `crypto.subtle` exists; X25519 through WebCrypto only when it computes RFC 7748's vector, `@noble` otherwise. A low-order X25519 public key throws on both paths (WebCrypto's all-zero result is refused explicitly, as `@noble` does). The switch (`setCipherBackend`) is exported from `cipher.ts` for tests only, not from the package. Site: `packages/common/src/cipher.ts` header.
10. **`newULID` moved to `@missiv/common`** (the client needs it for messageIDs); the server's `storage/ids.ts` re-exports it. Site: `packages/common/src/ids.ts`.
11. **`@missiv/common` gained a test suite** (vitest, `src/*.test.ts`, excluded from its build so `dist` stays test-free), where the vectors run on both backends; the client-server suite covers `composeMessage` / `openMessage` against the in-process key directory (`test/client-server/test/message-format.test.ts`).
