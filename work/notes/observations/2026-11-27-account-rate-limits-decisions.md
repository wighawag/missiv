# account-rate-limits: decisions made while building

2026-11-27, task `account-rate-limits` (spec `scalable-direct-messaging`, story 27). Choices the task and the ADRs left open (no ADR mentions rate limits), each recorded so a reviewer can ratify or reverse it. The code-level ones are also in the JSDoc of `packages/server/src/rate-limit.ts`.

1. **The send bucket is keyed by account AND domain** (`${domain}:${account}` in `packages/server/src/api/messages/index.ts`). A session token is per domain and so will be the Inbox Durable Object, so the budget follows it: the same wallet in two apps has two budgets. Alternative: one budget per address across domains. Rejected because one app's abuse would then throttle the account in another app, and a Durable Object per (domain, account) could not hold a cross-domain bucket.
2. **One IP bucket shared by `/api/session` and `register`**, charged before the signature check (`limitPerIP`, a middleware ahead of `setup`; on `register` only, not the rest of `/api/user`). The task says "a coarse per-IP bucket on `/session` and `register`". Alternative: two buckets. Rejected: both are the expensive signed entry points, and one budget is the coarser, simpler limit. Touches nothing else: the token routes and sends are never charged per IP.
3. **A request whose IP the platform does not know is not limited per IP.** One shared bucket for "unknown" would refuse every such client together (all clients behind a proxy the platform cannot see through, or every `app.request` in tests). Alternative: an `unknown` key. Rejected for that reason; the send budget still applies to them.
4. **`ServerOptions.inProcessRooms.getIP` moved to a top-level `ServerOptions.getIP`** (breaking, in the changeset), used by the per-IP limit and by in-process rooms. The cf-worker now sets it from `CF-Connecting-IP`. Alternative: a second `getIP` beside the rooms' one. Rejected as the same concept twice. The Node platform uses the socket's address: behind a reverse proxy every client is the proxy's IP (one budget), the same limitation the Bun platform already marks with a TODO.
5. **Defaults**: send 20 at once, 1 a second sustained; IP 30 at once, 0.5 a second (`DEFAULT_TOKEN_BUCKETS`). The env (`RATE_LIMIT_SEND_BURST`, `RATE_LIMIT_SEND_REFILL_PER_SECOND`, `RATE_LIMIT_IP_BURST`, `RATE_LIMIT_IP_REFILL_PER_SECOND`) overrides each. A value that is not a positive number fails the request that reads it (an internal error naming the variable), as a misconfigured `SESSION_SECRET` says so on the first call. There is no "off" switch; a very large burst is the way to lift a limit (the load harness and the client-server test harness do so for sends).
6. **A refused request takes no token** (no penalty), and counts as a use for the least-recently-used bound, so a key kept busy at its limit is the last one `maxKeys` (100 000) drops and resets.
7. **Idle eviction is "refilled to the burst"**: such a bucket answers exactly as a new one would, so dropping it changes nothing observable; a sweep runs at most once per refill time (an empty bucket's time to fill, at least 1 s). The room limiters use the same idea (`RateLimiter.isIdleAt`: its limit has caught up with the clock), swept at most once a second.
8. **`createInProcessRooms` hands a room a stub that looks its limiter up at each call** instead of the limiter itself. A room keeps its `RateLimiterClient`'s stub for the socket's life, so without this an eviction followed by a new connection from the same IP would give that IP two budgets. It also adds `rateLimiterCount()`, the observable the eviction test needs.
9. **The room limiter's back-to-back refusal** (`room-rate-limiter-refuses-back-to-back-messages.md`) is not fixed here: rooms are spec `scalable-rooms`. The new buckets answer synchronously in the charged request, so they do not have that defect.
10. **`TokenBuckets.take` may return a promise**, so the send's bucket can move into the Inbox Durable Object (task `cloudflare-durable-object-stores`) behind `ServerOptions.getTokenBuckets` without changing the routes. Until then Cloudflare's buckets are per isolate, an approximation (one budget per isolate, not per account globally).
