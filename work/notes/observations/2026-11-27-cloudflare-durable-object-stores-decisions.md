# cloudflare-durable-object-stores: decisions made while building

2026-11-27, task `cloudflare-durable-object-stores` (spec `scalable-direct-messaging`, stories 24 and 25). Choices ADR-0005 and ADR-0006 left open, each recorded so a reviewer can ratify or reverse it. The code-level ones are also in the module JSDoc at their site (`platforms/cf-worker/src/stores/conversation.ts`, `inbox.ts`, `index.ts`, `packages/server/src/stores/cache.ts`).

1. **The Inbox object pushes its own frames; the server only routes the socket** (`LiveInboxRouter`, `ServerOptions.getLiveInboxRouter`, `getRoutedInboxAPI` in `packages/server/src/api/inbox/index.ts`). The Inbox object holds the sockets and the rows, so it pushes `message` and `conversation` frames whenever it applies an update, accept, reject or markRead, and the core's `deliverAppended` / `deliverConversation` publish nothing there (they still ask `isOnline` for `PUSH_SKIP_WHEN_ONLINE`). Alternative: give cf-worker a `LiveInbox` whose `publish` is an RPC to the Inbox object; rejected, it costs three calls per member per send (online?, the row, publish) where one already happens, and a retried update would push nothing. A new port next to `LiveInbox`/`LiveInboxHost`, not a re-meaning of them: `LiveInbox` stays "the server publishes". Touches the `live-inbox-channel` route (now shared token check `checkInboxUpgrade`) and `delivery.ts`.
2. **The Conversation object awaits both inbox updates before the send answers**, and retries a failed one from an outbox by its alarm (1 s, doubling, at most 5 min, without end; it never throws from `alarm()`, so the runtime's 6-retry limit never applies). Alternative: answer at once and update after the response (`waitUntil`); rejected, a list read right after a send would miss it, unlike Node/Bun. So `AppendResult.pendingInboxUpdates` is empty on Cloudflare too (its JSDoc now says a store may own its retries). Touches nothing outside cf-worker.
3. **The outbox keeps every pending update (one per member and seq), delivered in seq order**, not only the newest per member: the newest can lose what an older carried (the sender's own message accepting its row).
4. **Blocks: the Inbox is the authority, the Conversation object holds a versioned copy.** The copy is read from both Inboxes before the first append, kept current by the blocker's Inbox (each change one version higher, applied only above the stored one), and the recipient's Inbox refuses an update from a member it blocks (`{blocked: true}`), which makes the Conversation object hide that message from it and record the block: this closes the window between a block and its propagation. Propagation targets every Conversation object that read the Inbox's block state or delivered to it (`shared`), not only those with a row, so an unblock also reaches a conversation whose every message was hidden. Propagation is awaited by `reject` / `unblock` and retried by the Inbox's alarm. Alternative: no copy, ask the recipient's Inbox at every append; rejected, ADR-0006 asks for the propagation, and it would add a call to every send. Note: CF's `Inbox.update` (the port) refuses an update from a blocked member too, where SQL's does not (the SQL send reads blocks in its own transaction).
5. **A `sync` heals the inbox row** (`answerSync`, shared by Node/Bun and the Inbox object): when the newest message it sends is above the row's `lastSeq`, it applies the update that message should have made. This is what makes "the client's sync heals the list meanwhile" true on Cloudflare while an update is being retried; on SQL it never applies. Alternative: leave the row until the alarm; rejected, the list would disagree with the messages the client just received.
6. **The key directory cache** (`cachedKeyDirectory`, 5 s, found lookups only, per isolate, at most 10 000 entries; a registration through it forgets that user's entries). For up to 5 s another isolate may accept a replaced signing key or refuse the new one on a send (`forbidden`, the client re-sends). Alternatives: no cache (a D1 read per send and per push); cache absences (a fresh registration refused for the TTL). Touches the send route's "current key set" check and the push's recipient lookup, on cf-worker only.
7. **D1 keeps the shared migrations**: the cf-worker's D1 still gets `Messages`, `Inbox` and `Blocks` (empty, unused). Alternative: a cf-only migrations directory with the directory's tables; rejected, a second copy of the schema to keep in step for three empty tables. The `wrangler.toml` comment says so.
8. **Compatibility date 2023-08-14 to 2025-03-10**, for Durable Object RPC (2024-04-03 or later). It also changes the defaults the rooms and rate limiters run with (nodejs_compat v2 among them); the cf-worker tests and the `wrangler dev` run passed with it, rooms were not rerun there (they 500 at the upgrade before this task: observation `cf-worker-room-upgrade-500-on-wrangler-dev`).
9. **The cf-worker's tests use `@cloudflare/vitest-pool-workers` 0.8.2** (the release pinned to the repo's wrangler 4.2.0 and vitest 3.0; the package is renamed `@cloudflare/vitest-plugin` upstream), one runtime with shared storage, as WebSockets in Durable Objects require. The store contract's statement-count test is registered only for implementations on one SQL database (`StoresImplementation` in `packages/server/test/store-contract.ts`).
10. **Failure injection through seams**: `ServerObjectConversation.inboxOf` and `ServerObjectInbox.conversationOf` are protected methods a test replaces on the live instance (`runInDurableObject`). No test-only flag in production code.
