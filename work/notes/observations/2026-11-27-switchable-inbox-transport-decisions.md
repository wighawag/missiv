# Decisions made while building switchable-inbox-transport

In-scope choices the task left open, one per entry, for the reviewer and the human to ratify or reverse. The wire ones (1 to 5) are what clients are built against; their JSDoc is `packages/common/src/inbox.ts`, and ADR-0006's amendment states them.

1. **The version is the highest row's, not a separate counter**: a change of a row sets its `version` to `MAX(version) + 1` of the user's rows in the domain, in the statement that changes it (SQL: migration `0003_inbox_version`, `nextVersion` in `packages/server/src/stores/sql/messaging.ts`; the Inbox Durable Object: `NEXT_VERSION`). So a send stays six statements (the contract's count and query plans still hold), and no second write can disagree with the rows. Alternatives: an `InboxVersions` table bumped in the same transaction (one more statement per member, and the "only when the row changed" condition repeated), or SQLite triggers (the migrations runner splits on `;`, and the rule would hide from the code). Rows stored before the migration are numbered by `rowid`.
2. **`unblock` takes no version**, although the task lists it: it changes no inbox row (it deletes a block), so a poll would report a change with nothing in it. Likewise an accept of an accepted row, a reject of a rejected one and a markRead that reads nothing new take none (these statements gained a "changed" condition). Touches `Inbox` port semantics on both implementations.
3. **The version rides inside the row** (`Conversation.version`, required) rather than beside it on the `conversation` frame: the rows of `listConversations`, `/inbox/changes` and the frames carry it alike, and a client never has to pair a frame field with its row. Touches the `Conversation` type every client reads (a new field; older clients ignore it).
4. **Paging by version**: `{version, conversations, hasMore}`, the rows oldest change first; with `hasMore` the answered `version` is the page's last row's, so a client always polls next from the answered `version`. "Paged like `listConversations`" was read as a page size (`limit`, at most 100) and a continuation, not its opaque cursor. Alternative: a `cursor` string as `listConversations` has (one more concept for a value that is already a number).
5. **A `since` above the inbox's version is answered as `since` 0** (every row), not `unchanged`: only a reset database produces it, and `unchanged` would leave that client silent until its version was passed again. Site: `SQLInbox.changes`, `ServerObjectInbox.changes`.
6. **The in-memory version on Node.js and Bun is used only where the process holds the sockets (`liveInbox`) AND `INBOX_TRANSPORTS` offers the socket**; with `poll` alone every poll reads its version from SQL. The task asks for both "an unchanged poll touches no database" and "the SQL read stays correct for several instances", and `poll` alone is the documented several-instance setting. Alternative: an explicit env switch (a misconfigured multi-instance deployment would then drop messages silently). Cost measured: about 0.065 ms of server time per empty poll from memory, 0.097 ms from SQL (`work/notes/findings/load-inbox-polling.md`). Site: `packages/server/src/stores/versions.ts` header; touches the meaning of `INBOX_TRANSPORTS`.
7. **`INBOX_TRANSPORTS` unset or empty means `socket,poll`; an unknown name fails the request that reads it** (500, as a malformed `RATE_LIMIT_*` does); a transport that is off answers 404 `not_found`, the socket's before any upgrade or token check. Site: `packages/server/src/transports.ts`. Touches every platform's configuration (a new user-visible env var with a default).
8. **The client's defaults**: `transport: 'auto'`, `pollIntervalMs` 5 s (the task's), `auto` falls back after 3 failed sockets in a row ("several"), a failure being a socket that closed before the server sent it anything (any frame from the server resets the count; `session-expired` is no failure), and retries the socket every 60 s while polling ("periodically"); a poll refused 404 sends `auto` back to the socket at once. `socketRetryIntervalMs` and `socketFailuresBeforePolling` are options of `openInboxChannel` only; the stores take `transport` and `pollIntervalMs`. Site: `packages/client/src/lib/inbox/index.ts` header.
9. **A poll from version 0 reads no message** (it only learns the rows), unless an earlier poll found the inbox empty: a new socket is pushed none of the past either, and the stores fetch and sync on the `onOpen` that follows. After that a changed row's messages are read from the highest seq the channel knows of that conversation, so a conversation no store opened still gets its new messages, as on the socket. The first look spans every page of that drain, and one cut short (an error, the channel stopped) is redone from version 0, so no page of it is read as a change. Site: the channel's `drain`.
10. **The load harness's Node.js target passes `INBOX_TRANSPORTS` from the harness's env**, so the several-instance path (version from SQL) can be measured. Site: `test/load/src/node-server.ts`.
11. **`POST /api/inbox/changes` is mounted behind the CORS middleware, the socket upgrades ahead of it**: a browser on another origin must read a poll's answer, while a 101 answer has no use for CORS headers (as on main before this task). Site: `createServer`.
12. **An admin `db-reset` clears the in-process version cache**, so a poll from before the reset reads the database again (a `since` above the inbox's version answered as 0, ADR-0006). Site: the admin API and `InboxVersionCache.clear`.

Noticed, not fixed: `PUSH_SKIP_WHEN_ONLINE` counts only open sockets as online, so a polling client is still pushed (consistent with its doc, "has the live inbox channel open" read as the socket; now said so in `docs/architecture.md`).
