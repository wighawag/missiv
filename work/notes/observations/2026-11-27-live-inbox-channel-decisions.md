# Decisions made while building live-inbox-channel

In-scope choices the task and ADR-0006 left open, one per entry, for the reviewer and the human to ratify or reverse. The wire ones (1 to 5) are what clients are built against; their JSDoc is `packages/common/src/inbox.ts`.

1. **The token is offered as the second WebSocket protocol**, `Sec-WebSocket-Protocol: missiv-inbox, <token>`, and the server selects `missiv-inbox` (a browser fails a handshake that selects no protocol it offered; the token is never echoed). ADR-0006 allowed this or a one-shot ticket from an HTTP call; the ticket is not built (an HTTP call and server state per connection for nothing the header lacks). The path is `GET /api/inbox/ws`, beside every other route under `/api` (ADR-0006 writes `/inbox/ws` as it writes `/session` for `/api/session`). Touches `cloudflare-durable-object-stores` (its Worker checks the same header before routing to the Inbox object). Site: `packages/server/src/api/inbox/index.ts`.
2. **A socket is for the token's domain and every namespace in it**, so one socket serves all of a client's stores. A `sync` names a conversation `<namespace>:<conversationID>` (`inboxConversationKey`; split on the last `:`, as a conversationID has none). Alternative: a socket per (domain, namespace) with a query parameter (one socket per namespace a client shows). Site: `inbox.ts`.
3. **`session-expired` is close code 4001** with reason `session-expired` (the application's range, RFC 6455 7.4.2). The client renews its session (`API.getSession(..., {renew: true})`) and reconnects at once; a socket refused before it opened also renews on its next attempt (the token may be stale: a rotated secret, a replaced key set), with backoff. Site: `inbox.ts`, `packages/client/src/lib/inbox/index.ts`.
4. **`sync` semantics**: per conversation the account is a member of, every message after the seq it can see (paged by 100 server-side, so a long absence costs one page of memory, and no more than reading it over HTTP), then its inbox row, then one `ready` per sync, syncs answered in the order sent. At most 1000 conversations per sync. A conversation the account is not a member of, or a malformed key, is skipped silently (as HTTP would refuse it); a frame that is not a valid sync closes the socket with 1008. The server sends `ready` only in answer to a sync, never on its own at open. Site: `answerSync` in `api/inbox/index.ts`.
5. **`accept`, `reject` and `markRead` push the changed inbox row to the user's own sockets** (ADR-0006 lists `conversation` frames without saying which changes send one). Without it the conversation list, which no longer polls, would keep a conversation unread after the conversation store (or another device) marked it read. `unblock` changes no row and pushes nothing. Site: `changed` in `api/private/index.ts`, `deliverConversation` in `src/delivery.ts`.
6. **`PUSH_SKIP_WHEN_ONLINE=true` is the "server option", an env var, off by default** (every recipient is pushed, online or not, as before). "Online" is any open socket of the recipient in the message's domain, whatever the namespace. Alternative: a `ServerOptions` field (code, not deployment, configuration; every other server setting is env). Touches every platform's env (documented in `docs/architecture.md` "Configuration"); only nodejs and bun hold sockets, so it does nothing on cf-worker yet. Site: `src/env.ts`, `deliverAppended`.
7. **The delivery runs after the response**, with the push (`waitUntil` where the platform has one), and a member's inbox row is read only when that member is online (`Inbox.getConversation`, a new port method), so a send to members without a socket costs no statement more (the send's bounded-statements test is unchanged). Frames may therefore arrive before or after the sender's HTTP answer and out of order between sends; clients apply messages by seq and rows by `lastSeq`. Site: `src/delivery.ts`, `stores/ports.ts`.
8. **The live side is a `LiveInbox` port (`publish`, `isOnline`, both async) and a `LiveInboxHost` that also `connect`s sockets**, passed as `ServerOptions.liveInbox`; `createInProcessLiveInbox` is the Map behind it on nodejs and bun. The route exists only when a platform passes one: **cf-worker has no live channel until `cloudflare-durable-object-stores`, and since the client no longer polls, a cf-worker deployment's open conversations and lists update only when reopened or after a send of their own** (the client retries the socket with backoff, which 404s there). Touches `cloudflare-durable-object-stores`, which must land before a cf-worker release of this client. Site: `types.ts`, `src/live.ts`.
9. **One client channel per (endpoint, domain, signing key), shared through a module-level map**, open while any store of that account listens, rather than a channel object the app passes to each store (an API change for every caller). The conversation list refetches its first page each time the channel opens (a new conversation started while away is not in any sync); a conversation fetches its newest page once, then syncs on every (re)connection and right after that first page (closing the gap between the page's read and the socket's opening). A message a store sends is added from the send's answer, so it shows whether or not the socket is up; its echo is ignored by seq. Site: `packages/client/src/lib/inbox/index.ts`, the two stores' JSDoc.
10. **`pollingInterval` is removed from both stores (breaking), replaced by `retryDelayMs`** (the first retry delay of a failed fetch or a lost socket, doubled up to 30 s) and `createWebSocket`; `lifecycle.ts`'s `poll` is replaced by `retryUntilDone`, which stops at the first success. Site: `packages/client/src/lib/utils/lifecycle.ts`.
11. **`test/client-server` serves its harness on a loopback port** (`h.listen()`, `@hono/node-server` and `@hono/node-ws`, as the Node.js platform) for the live channel and the stores that use it, with Node's own WebSocket as the client, rather than fake sockets wired to the route's events: the upgrade refusal and the protocol selection are then the real ones. The registration tests keep `app.request`. Site: `test/client-server/test/setup.ts`.
12. **The load harness's `live` scenario is the `send` loop with every user's socket open**, timing each message to the recipient's socket (`live`) and to the sender's own (`live-own`); it shares the world of `send`, `read` and `list`. Numbers: `work/notes/findings/load-live-inbox.md`. Site: `runLive` in `test/load/src/scenarios.ts`.
